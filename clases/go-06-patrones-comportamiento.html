Patrones de Diseño II: De Comportamiento

Los 10 patrones de comportamiento organizan cómo colaboran los objetos: quién atiende una petición, cómo se notifican eventos, cómo se recorren estructuras y cómo cambian los algoritmos. Varios de ellos ya están escondidos dentro del intérprete del libro.

1. Patrones de comportamiento: repaso

En Go V vimos cómo crear y componer objetos. Los patrones de comportamiento tratan sobre algoritmos y responsabilidades. Tres de ellos ya los usamos sin nombrarlos:

Iterator

lexer.NextToken() entrega un token a la vez sin exponer el string interno.

Strategy

prefixParseFns/infixParseFns: una función de parsing distinta por token.

Visitor (alternativa)

Eval recorre el AST con un type switch; un Visitor haría lo mismo con métodos Accept.

Referencia: el catálogo de Refactoring.Guru explica cada patrón con diagramas y ejemplos en Go. Aquí los vemos aplicados al mundo de los intérpretes.

3. Chain of Responsibility

Comportamiento ejemplos/patrones/chain-of-responsibility Catálogo de referencia

Intención

Pasar una petición por una cadena de manejadores; cada uno decide si la atiende o la pasa al siguiente.

Problema en ZeldaInterpreter

El REPL debe reconocer comandos (:help, :env, :quit) antes de tratar la línea como código Monkey.

Úsalo cuando…

Cuando varios objetos pueden atender una petición y el orden importa.

Evítalo si…

Si siempre la atiende el mismo manejador.

En Go: Una interfaz Handler y un struct base embebido con el puntero al siguiente.
En el intérprete: Comandos del REPL y, en general, cualquier cadena de middlewares.
ejemplos/patrones/chain-of-responsibility/main.go
// Chain of Responsibility: pasar una petición por una cadena de manejadores
// hasta que uno la atienda. Ejemplo: comandos del REPL antes de evaluar código.
package main

import (
	"fmt"
	"strings"
)

type Handler interface {
	Handle(line string) string
	SetNext(h Handler) Handler
}

// base implementa el "pasar al siguiente"; los manejadores concretos la embeben.
type base struct{ next Handler }

func (b *base) SetNext(h Handler) Handler {
	b.next = h
	return h
}

func (b *base) pass(line string) string {
	if b.next == nil {
		return "(nadie atendió la línea)"
	}
	return b.next.Handle(line)
}

type emptyLine struct{ base }

type command struct {
	base
	name, reply string
}

type evaluate struct{ base }

func (h *emptyLine) Handle(l string) string {
	if strings.TrimSpace(l) == "" {
		return "(nada que evaluar)"
	}
	return h.pass(l)
}

func (h *command) Handle(l string) string {
	if strings.TrimSpace(l) == h.name {
		return h.reply
	}
	return h.pass(l)
}

func (h *evaluate) Handle(l string) string { return "evaluando: " + l }

func main() {
	chain := &emptyLine{}
	chain.SetNext(&command{name: ":help", reply: "comandos: :help :env"}).
		SetNext(&command{name: ":env", reply: "x = 5"}).
		SetNext(&evaluate{})

	for _, in := range []string{"", ":help", ":env", "1 + 2"} {
		fmt.Printf("%-8q -> %s\n", in, chain.Handle(in))
	}
}
$ go run ./patrones/chain-of-responsibility
""       -> (nada que evaluar)
":help"  -> comandos: :help :env
":env"   -> x = 5
"1 + 2"  -> evaluando: 1 + 2

4. Command

Comportamiento ejemplos/patrones/command Catálogo de referencia

Intención

Encapsular una petición como un objeto para guardarla, encolarla, deshacerla o rehacerla.

Problema en ZeldaInterpreter

Queremos que el REPL permita :undo de la última sentencia let.

Úsalo cuando…

Historial, deshacer/rehacer, colas de tareas, macros.

Evítalo si…

Para acciones simples que nunca se guardan ni se deshacen.

En Go: Una interfaz Execute/Undo o simplemente valores de tipo func().
En el intérprete: Historial del REPL; la secuela del libro compila a instrucciones (opcodes) que son comandos.
ejemplos/patrones/command/main.go
// Command: encapsular una petición como objeto para guardarla, deshacerla o rehacerla.
// Ejemplo: historial del REPL con :undo.
package main

import "fmt"

type Env map[string]int

type Command interface {
	Execute(env Env)
	Undo(env Env)
}

type LetCommand struct {
	Name    string
	Value   int
	prev    int
	existed bool
}

func (c *LetCommand) Execute(env Env) {
	c.prev, c.existed = env[c.Name]
	env[c.Name] = c.Value
}

func (c *LetCommand) Undo(env Env) {
	if c.existed {
		env[c.Name] = c.prev
	} else {
		delete(env, c.Name)
	}
}

type History struct {
	env  Env
	done []Command
}

func (h *History) Run(c Command) {
	c.Execute(h.env)
	h.done = append(h.done, c)
}

func (h *History) Undo() {
	if len(h.done) == 0 {
		return
	}
	last := h.done[len(h.done)-1]
	h.done = h.done[:len(h.done)-1]
	last.Undo(h.env)
}

func main() {
	h := &History{env: Env{}}
	h.Run(&LetCommand{Name: "x", Value: 1})
	h.Run(&LetCommand{Name: "x", Value: 2})
	h.Run(&LetCommand{Name: "y", Value: 9})
	fmt.Println("antes: ", h.env)
	h.Undo() // deshace let y
	h.Undo() // deshace let x = 2
	fmt.Println("después:", h.env)
}
$ go run ./patrones/command
antes:  map[x:2 y:9]
después: map[x:1]

5. Iterator

Comportamiento ejemplos/patrones/iterator Catálogo de referencia

Intención

Recorrer los elementos de una colección sin exponer su estructura interna.

Problema en ZeldaInterpreter

El parser necesita tokens uno a uno sin saber cómo el lexer los obtiene del texto.

Úsalo cuando…

Colecciones con recorridos personalizados o perezosos.

Evítalo si…

Si basta con un slice y for range.

En Go: Método Next() o funciones iter.Seq que funcionan con for range.
En el intérprete: ¡El lexer! NextToken() es un iterador; con Go 1.23 puede exponerse como iter.Seq[Token].
ejemplos/patrones/iterator/main.go
// Iterator: recorrer una colección sin exponer su estructura interna.
// El lexer ya es un iterador (NextToken). Con Go 1.23 también podemos usar range sobre funciones.
package main

import (
	"fmt"
	"iter"
	"strings"
)

type Token struct{ Type, Literal string }

type Lexer struct {
	words []string
	pos   int
}

func New(src string) *Lexer { return &Lexer{words: strings.Fields(src)} }

// Estilo clásico del libro: llamar NextToken() hasta EOF.
func (l *Lexer) NextToken() Token {
	if l.pos >= len(l.words) {
		return Token{"EOF", ""}
	}
	w := l.words[l.pos]
	l.pos++
	if w == "let" {
		return Token{"LET", w}
	}
	return Token{"WORD", w}
}

// Estilo Go 1.23: un iter.Seq que funciona con for range.
func (l *Lexer) All() iter.Seq[Token] {
	return func(yield func(Token) bool) {
		for {
			t := l.NextToken()
			if t.Type == "EOF" || !yield(t) {
				return
			}
		}
	}
}

func main() {
	l := New("let x = 5 ;")
	for tok := l.NextToken(); tok.Type != "EOF"; tok = l.NextToken() {
		fmt.Print(tok.Type, " ")
	}
	fmt.Println()

	for tok := range New("let y = x ;").All() {
		fmt.Print(tok.Literal, " ")
		if tok.Literal == "=" {
			break // el iterador se detiene limpiamente
		}
	}
	fmt.Println()
}
$ go run ./patrones/iterator
LET WORD WORD WORD WORD 
let y =

6. Mediator

Comportamiento ejemplos/patrones/mediator Catálogo de referencia

Intención

Centralizar la comunicación entre componentes para que no dependan unos de otros directamente.

Problema en ZeldaInterpreter

Un editor, una consola y un panel de errores deben coordinarse; si se llaman entre sí, todo queda acoplado.

Úsalo cuando…

Interfaces gráficas, salas de chat, sistemas con muchas interacciones cruzadas.

Evítalo si…

Si el mediador termina concentrando toda la lógica del sistema.

En Go: Un struct que conoce a todos los componentes y un método Notify.
En el intérprete: Una “mini IDE” web para Monkey que coordina editor, salida y errores (como el simulador del curso).
ejemplos/patrones/mediator/main.go
// Mediator: los componentes no se hablan entre sí; se comunican a través de un mediador.
// Ejemplo: mini IDE con editor, consola y panel de errores coordinados por la sesión.
package main

import "fmt"

type Mediator interface {
	Notify(sender, event, data string)
}

type Editor struct{ m Mediator }
type Console struct{ lines []string }
type ErrorPanel struct{ errors []string }

func (e *Editor) Submit(code string) { e.m.Notify("editor", "submit", code) }
func (c *Console) Print(s string)    { c.lines = append(c.lines, s) }
func (p *ErrorPanel) Show(s string)  { p.errors = append(p.errors, s) }
func (p *ErrorPanel) Clear()         { p.errors = nil }

// Session es el mediador: conoce a todos y decide quién reacciona a qué.
type Session struct {
	editor  *Editor
	console *Console
	panel   *ErrorPanel
}

func NewSession() *Session {
	s := &Session{console: &Console{}, panel: &ErrorPanel{}}
	s.editor = &Editor{m: s}
	return s
}

func (s *Session) Notify(sender, event, data string) {
	if sender == "editor" && event == "submit" {
		s.panel.Clear()
		if data == "" {
			s.panel.Show("código vacío")
			return
		}
		s.console.Print(">> " + data)
	}
}

func main() {
	s := NewSession()
	s.editor.Submit("let x = 5;")
	s.editor.Submit("")
	fmt.Println("consola:", s.console.lines)
	fmt.Println("errores:", s.panel.errors)
}
$ go run ./patrones/mediator
consola: [>> let x = 5;]
errores: [código vacío]

7. Memento

Comportamiento ejemplos/patrones/memento Catálogo de referencia

Intención

Capturar y restaurar el estado interno de un objeto sin exponer sus detalles.

Problema en ZeldaInterpreter

Si un programa falla a mitad de ejecución, el REPL debería volver al entorno anterior.

Úsalo cuando…

Deshacer, puntos de control (checkpoints) y transacciones.

Evítalo si…

Si el estado es enorme y copiarlo es demasiado costoso.

En Go: Un tipo con campos privados que solo el dueño sabe crear y leer; maps.Clone ayuda.
En el intérprete: Guardar el Environment antes de evaluar y restaurarlo si aparece un *object.Error.
ejemplos/patrones/memento/main.go
// Memento: guardar y restaurar el estado de un objeto sin romper su encapsulación.
// Ejemplo: si un programa falla a la mitad, el REPL restaura el entorno anterior.
package main

import (
	"errors"
	"fmt"
	"maps"
)

type Environment struct{ store map[string]int }

// Snapshot es el memento: una instantánea opaca (campo privado).
type Snapshot struct{ store map[string]int }

func (e *Environment) Save() Snapshot     { return Snapshot{store: maps.Clone(e.store)} }
func (e *Environment) Restore(s Snapshot) { e.store = maps.Clone(s.store) }

func runProgram(env *Environment, stmts []string) error {
	for _, s := range stmts {
		if s == "ERROR" {
			return errors.New("type mismatch: INTEGER + BOOLEAN")
		}
		env.store[s] = len(env.store) + 1
	}
	return nil
}

func main() {
	env := &Environment{store: map[string]int{"x": 1}}

	snap := env.Save() // el REPL (caretaker) guarda antes de ejecutar
	err := runProgram(env, []string{"a", "b", "ERROR", "c"})
	fmt.Println("tras el error:", env.store, "|", err)

	env.Restore(snap)
	fmt.Println("restaurado:   ", env.store)
}
$ go run ./patrones/memento
tras el error: map[a:2 b:3 x:1] | type mismatch: INTEGER + BOOLEAN
restaurado:    map[x:1]

8. Observer

Comportamiento ejemplos/patrones/observer Catálogo de referencia

Intención

Notificar automáticamente a varios suscriptores cuando ocurre un evento.

Problema en ZeldaInterpreter

Queremos un tracer, un profiler y un depurador escuchando lo que hace el evaluador sin modificarlo cada vez.

Úsalo cuando…

Eventos, notificaciones, interfaces reactivas.

Evítalo si…

Si el orden de las notificaciones importa o hay demasiados observadores encadenados.

En Go: Un slice de interfaces Observer, o canales cuando los suscriptores son goroutines.
En el intérprete: Eventos call/error del evaluador para depurar programas Monkey.
ejemplos/patrones/observer/main.go
// Observer: un objeto notifica a sus suscriptores cuando ocurre algo.
// Ejemplo: el evaluador emite eventos; un tracer y un profiler los escuchan.
package main

import "fmt"

type Event struct {
	Kind string // "call" | "error"
	Name string
}

type Observer interface{ OnEvent(e Event) }

type Evaluator struct{ observers []Observer }

func (ev *Evaluator) Subscribe(o Observer) { ev.observers = append(ev.observers, o) }

func (ev *Evaluator) emit(e Event) {
	for _, o := range ev.observers {
		o.OnEvent(e)
	}
}

func (ev *Evaluator) Call(fn string) {
	ev.emit(Event{Kind: "call", Name: fn})
	if fn == "foo" {
		ev.emit(Event{Kind: "error", Name: "identifier not found: foo"})
	}
}

type Tracer struct{}

func (Tracer) OnEvent(e Event) { fmt.Printf("[trace] %-5s %s\n", e.Kind, e.Name) }

type Profiler struct{ calls map[string]int }

func (p *Profiler) OnEvent(e Event) {
	if e.Kind == "call" {
		p.calls[e.Name]++
	}
}

func main() {
	ev := &Evaluator{}
	prof := &Profiler{calls: map[string]int{}}
	ev.Subscribe(Tracer{})
	ev.Subscribe(prof)

	for _, f := range []string{"fib", "fib", "len", "foo"} {
		ev.Call(f)
	}
	fmt.Println("perfil:", prof.calls)
}
$ go run ./patrones/observer
[trace] call  fib
[trace] call  fib
[trace] call  len
[trace] call  foo
[trace] error identifier not found: foo
perfil: map[fib:2 foo:1 len:1]

9. State

Comportamiento ejemplos/patrones/state Catálogo de referencia

Intención

Permitir que un objeto cambie su comportamiento cuando cambia su estado interno.

Problema en ZeldaInterpreter

Un escáner se comporta distinto dentro de un string, de un comentario o en modo normal.

Úsalo cuando…

Máquinas de estados: lexers, protocolos, flujos de interfaz.

Evítalo si…

Si solo hay dos estados y un if es suficiente.

En Go: Una interfaz State o funciones de estado type stateFn func(*Lexer) stateFn.
En el intérprete: Un lexer con modos (string, comentario). El REPL podría tener modo normal y modo multilínea.
ejemplos/patrones/state/main.go
// State: un objeto cambia su comportamiento cuando cambia su estado interno.
// Ejemplo: un escáner con modos Normal / DentroDeString / DentroDeComentario.
package main

import "fmt"

type State interface {
	Read(s *Scanner, ch byte)
}

type Scanner struct {
	state  State
	tokens []string
	buf    []byte
}

type normal struct{}
type inString struct{}
type inComment struct{}

func (normal) Read(s *Scanner, ch byte) {
	switch ch {
	case '"':
		s.state = inString{}
	case '#':
		s.state = inComment{}
	case ' ', '\n':
		// ignorar espacios
	default:
		s.tokens = append(s.tokens, string(ch))
	}
}

func (inString) Read(s *Scanner, ch byte) {
	if ch == '"' {
		s.tokens = append(s.tokens, "STRING("+string(s.buf)+")")
		s.buf = nil
		s.state = normal{}
		return
	}
	s.buf = append(s.buf, ch)
}

func (inComment) Read(s *Scanner, ch byte) {
	if ch == '\n' {
		s.state = normal{}
	}
}

func main() {
	s := &Scanner{state: normal{}}
	src := "x+\"hola mundo\" # esto es un comentario\ny"
	for i := 0; i < len(src); i++ {
		s.state.Read(s, src[i]) // el comportamiento depende del estado actual
	}
	fmt.Println(s.tokens)
}
$ go run ./patrones/state
[x + STRING(hola mundo) y]

10. Strategy

Comportamiento ejemplos/patrones/strategy Catálogo de referencia

Intención

Definir una familia de algoritmos intercambiables detrás de una misma interfaz.

Problema en ZeldaInterpreter

Cada operador o tipo de token necesita su propio algoritmo, y queremos agregar nuevos sin tocar el núcleo.

Úsalo cuando…

Algoritmos que varían según el contexto y se eligen en tiempo de ejecución.

Evítalo si…

Si hay un solo algoritmo y no se espera que cambie.

En Go: Tipos función guardados en un map; o una interfaz si la estrategia tiene estado.
En el intérprete: ¡El Pratt parser! prefixParseFns e infixParseFns son mapas de estrategias por token (Semana 5).
ejemplos/patrones/strategy/main.go
// Strategy: una familia de algoritmos intercambiables detrás de una misma interfaz.
// El Pratt parser lo usa: cada token tiene su "estrategia" de parsing (prefixParseFns).
package main

import (
	"errors"
	"fmt"
)

// Estrategia como tipo función (la forma más idiomática en Go).
type BinaryOp func(a, b int64) (int64, error)

var operators = map[string]BinaryOp{
	"+": func(a, b int64) (int64, error) { return a + b, nil },
	"-": func(a, b int64) (int64, error) { return a - b, nil },
	"*": func(a, b int64) (int64, error) { return a * b, nil },
	"/": func(a, b int64) (int64, error) {
		if b == 0 {
			return 0, errors.New("division by zero")
		}
		return a / b, nil
	},
}

func evalInfix(op string, a, b int64) (int64, error) {
	strategy, ok := operators[op]
	if !ok {
		return 0, fmt.Errorf("unknown operator: INTEGER %s INTEGER", op)
	}
	return strategy(a, b)
}

// Estrategia como interfaz: motores de ejecución intercambiables.
type Engine interface{ Name() string }
type TreeWalker struct{}
type BytecodeVM struct{}

func (TreeWalker) Name() string { return "tree-walking (este curso)" }
func (BytecodeVM) Name() string { return "bytecode + VM (la secuela del libro)" }

func main() {
	for _, op := range []string{"+", "*", "/", "%"} {
		v, err := evalInfix(op, 12, 0)
		if err != nil {
			fmt.Printf("12 %s 0 -> ERROR: %v\n", op, err)
			continue
		}
		fmt.Printf("12 %s 0 -> %d\n", op, v)
	}
	for _, e := range []Engine{TreeWalker{}, BytecodeVM{}} {
		fmt.Println("motor:", e.Name())
	}
}
$ go run ./patrones/strategy
12 + 0 -> 12
12 * 0 -> 0
12 / 0 -> ERROR: division by zero
12 % 0 -> ERROR: unknown operator: INTEGER % INTEGER
motor: tree-walking (este curso)
motor: bytecode + VM (la secuela del libro)

11. Template Method

Comportamiento ejemplos/patrones/template-method Catálogo de referencia

Intención

Fijar el esqueleto de un algoritmo y dejar que ciertos pasos los implementen otros.

Problema en ZeldaInterpreter

Todo intérprete sigue tokenizar → validar → ejecutar, pero cada lenguaje lo hace distinto.

Úsalo cuando…

Algoritmos con pasos fijos y puntos de extensión bien definidos.

Evítalo si…

Si los pasos cambian de orden según el caso.

En Go: Sin clases abstractas: una función que recibe una interfaz con los pasos.
En el intérprete: El pipeline lexer → parser → evaluador; también el patrón de pruebas table-driven (mismo esqueleto, distintos casos).
ejemplos/patrones/template-method/main.go
// Template Method: el esqueleto de un algoritmo queda fijo y los pasos variables se delegan.
// En Go no hay clases abstractas: el esqueleto es una función y los pasos, una interfaz.
package main

import (
	"fmt"
	"strings"
)

// Language define los pasos que cada lenguaje debe proveer.
type Language interface {
	Tokenize(src string) []string
	Validate(tokens []string) error
	Execute(tokens []string) string
}

// Run es el método plantilla: el orden de los pasos nunca cambia.
func Run(lang Language, src string) string {
	toks := lang.Tokenize(src)
	if err := lang.Validate(toks); err != nil {
		return "error: " + err.Error()
	}
	return lang.Execute(toks)
}

type Calc struct{}

func (Calc) Tokenize(s string) []string { return strings.Fields(s) }
func (Calc) Validate(t []string) error {
	if len(t)%2 == 0 {
		return fmt.Errorf("expresión incompleta: %v", t)
	}
	return nil
}
func (Calc) Execute(t []string) string { return "calculando " + strings.Join(t, "") }

type Shout struct{}

func (Shout) Tokenize(s string) []string { return strings.Split(s, "") }
func (Shout) Validate([]string) error    { return nil }
func (Shout) Execute(t []string) string  { return strings.ToUpper(strings.Join(t, "")) }

func main() {
	fmt.Println(Run(Calc{}, "1 + 2"))
	fmt.Println(Run(Calc{}, "1 +"))
	fmt.Println(Run(Shout{}, "monkey"))
}
$ go run ./patrones/template-method
calculando 1+2
error: expresión incompleta: [1 +]
MONKEY

12. Visitor

Comportamiento ejemplos/patrones/visitor Catálogo de referencia

Intención

Agregar operaciones nuevas a una jerarquía de tipos sin modificar esos tipos.

Problema en ZeldaInterpreter

Sobre el mismo AST queremos evaluar, imprimir, contar nodos, verificar tipos… sin llenar cada nodo de métodos.

Úsalo cuando…

Estructuras estables (como un AST) con muchas operaciones distintas.

Evítalo si…

Si se agregan tipos de nodo con frecuencia: cada visitor debe actualizarse.

En Go: Métodos Accept(v Visitor) en cada nodo; en Go el type switch suele ser más simple.
En el intérprete: Alternativa al switch node := node.(type) de Eval; compiladores reales usan visitors para varias pasadas.
ejemplos/patrones/visitor/main.go
// Visitor: agregar operaciones nuevas a una jerarquía de nodos SIN modificar los nodos.
// El libro usa un type switch en Eval; el Visitor es la alternativa clásica de POO.
package main

import (
	"fmt"
	"strconv"
)

type Visitor interface {
	VisitInt(n *IntLit) any
	VisitInfix(n *Infix) any
}

type Node interface{ Accept(v Visitor) any }

type IntLit struct{ Value int }

type Infix struct {
	Left  Node
	Op    string
	Right Node
}

func (n *IntLit) Accept(v Visitor) any { return v.VisitInt(n) }
func (n *Infix) Accept(v Visitor) any  { return v.VisitInfix(n) }

// Operación 1: evaluar.
type Evaluator struct{}

func (Evaluator) VisitInt(n *IntLit) any { return n.Value }
func (e Evaluator) VisitInfix(n *Infix) any {
	l, r := n.Left.Accept(e).(int), n.Right.Accept(e).(int)
	switch n.Op {
	case "+":
		return l + r
	case "*":
		return l * r
	}
	return 0
}

// Operación 2: imprimir. Es nueva y no requirió tocar IntLit ni Infix.
type Printer struct{}

func (Printer) VisitInt(n *IntLit) any { return strconv.Itoa(n.Value) }
func (p Printer) VisitInfix(n *Infix) any {
	return "(" + n.Left.Accept(p).(string) + " " + n.Op + " " + n.Right.Accept(p).(string) + ")"
}

func main() {
	ast := &Infix{Left: &IntLit{1}, Op: "+", Right: &Infix{Left: &IntLit{2}, Op: "*", Right: &IntLit{3}}}
	fmt.Println(ast.Accept(Printer{}), "=", ast.Accept(Evaluator{}))
}
$ go run ./patrones/visitor
(1 + (2 * 3)) = 7

14. Ideas clave

Chain of Responsibility

Pasar una petición por una cadena de manejadores; cada uno decide si la atiende o la pasa al siguiente.

Command

Encapsular una petición como un objeto para guardarla, encolarla, deshacerla o rehacerla.

Iterator

Recorrer los elementos de una colección sin exponer su estructura interna.

Mediator

Centralizar la comunicación entre componentes para que no dependan unos de otros directamente.

Memento

Capturar y restaurar el estado interno de un objeto sin exponer sus detalles.

Observer

Notificar automáticamente a varios suscriptores cuando ocurre un evento.

Regla de oro en Go: empieza por lo más simple (funciones e interfaces pequeñas) y reconoce el patrón cuando aparezca; no al revés.
