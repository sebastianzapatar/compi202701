Concurrencia en Go: Goroutines, Canales y Sincronización

La concurrencia es la característica más famosa de Go. Aprenderemos a lanzar goroutines, comunicarlas con canales, evitar condiciones de carrera y aplicar patrones como pipelines y worker pools, siempre con ejemplos del mundo de los intérpretes.

Código ejecutable en ejemplos/concurrencia/ Simuladores de carrera y de canales

2Detectar y corregir condiciones de carrera con Mutex y -race.

1. Concurrencia no es paralelismo

Concurrencia

Es una forma de estructurar un programa como tareas independientes que pueden progresar de forma intercalada. Es sobre diseño.

Ej.: un REPL que lee la entrada mientras otra tarea evalúa con un límite de tiempo.

Paralelismo

Es ejecutar varias tareas literalmente al mismo tiempo en varios núcleos. Es sobre ejecución.

Ej.: evaluar 1000 archivos .mk usando los 8 núcleos del equipo.

En Go: escribes código concurrente con goroutines y canales; el runtime decide si se ejecuta en paralelo según runtime.GOMAXPROCS (por defecto, el número de núcleos). La idea clave del lenguaje: “no comuniques compartiendo memoria; comparte memoria comunicando”.

2. Goroutines y sync.WaitGroup

ejemplos/concurrencia/goroutines/main.go
// Goroutines, WaitGroup y Mutex: contar tokens de varios programas en paralelo.
package main

import (
	"fmt"
	"strings"
	"sync"
)

func countTokens(src string) int { return len(strings.Fields(src)) }

func main() {
	programs := []string{
		"let x = 5 ;",
		"let add = fn ( a , b ) { a + b } ;",
		"add ( 1 , 2 ) ;",
	}

	var (
		wg    sync.WaitGroup
		mu    sync.Mutex
		total int
	)
	for i, p := range programs {
		wg.Add(1)
		go func() { // desde Go 1.22 cada iteración tiene sus propias i y p
			defer wg.Done()
			n := countTokens(p)
			mu.Lock() // sección crítica: una sola goroutine a la vez
			total += n
			mu.Unlock()
			fmt.Printf("programa %d: %d tokens\n", i, n)
		}()
	}
	wg.Wait() // esperar a que todas terminen
	fmt.Println("total:", total)
}
$ go run ./concurrencia/goroutines (el orden puede variar)
programa 0: 5 tokens
programa 1: 15 tokens
programa 2: 7 tokens
total: 27
  • go f() lanza una goroutine: un hilo ligero (empieza con ~2 KB de pila) gestionado por el runtime.
  • Cuando main termina, todas las goroutines mueren: por eso esperamos con wg.Wait().
  • Patrón: wg.Add(1) antes de lanzar, defer wg.Done() dentro.
  • El orden de las líneas impresas no está garantizado.

3. Condiciones de carrera y sync.Mutex

Una condición de carrera ocurre cuando dos goroutines acceden a la misma variable al mismo tiempo y al menos una escribe. total += n parece una operación, pero son tres: leer, sumar y escribir.

Con carrera (incorrecto)
var total int
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        total++ // leer, sumar, escribir: ¡se intercalan!
    }()
}
wg.Wait()
fmt.Println(total) // a veces 1000, a veces 987, 994...
Corregido
var (
    mu    sync.Mutex
    total int
)
go func() {
    defer wg.Done()
    mu.Lock()
    total++ // sección crítica
    mu.Unlock()
}()

// Alternativas: sync/atomic para contadores,
// sync.RWMutex si hay muchas más lecturas que escrituras.
Detector de carreras: go run -race . y go test -race ./... instrumentan el programa y reportan cada acceso concurrente sin sincronizar. Úsalo siempre que haya goroutines.

Dos goroutines ejecutan counter++ (leer → sumar → escribir). Tú decides el orden en que el planificador las ejecuta. El resultado correcto es 2.

5. Canales: comunicar en vez de compartir

Operaciones básicas
ch := make(chan Token)     // sin buffer
bc := make(chan Token, 4)  // con buffer de 4

ch <- tok        // enviar
tok := <-ch      // recibir
tok, ok := <-ch  // ok == false si el canal está cerrado y vacío
close(ch)        // solo el EMISOR cierra

for tok := range ch { ... } // recibe hasta que se cierre

// Tipos direccionales: documentan y restringen el uso
func lex(src string) <-chan Token      // solo recibir
func worker(out chan<- Result)         // solo enviar

6. Simulador: un canal entre el lexer y el parser

El lexer envía los tokens de let x = 5; y el parser los recibe. Cambia la capacidad del canal y descubre cuándo se bloquea cada goroutine.

7. Un lexer concurrente

El lexer corre en su propia goroutine y el parser consume con range. Este diseño lo popularizó Rob Pike en su charla Lexical Scanning in Go y lo usa el paquete text/template de la biblioteca estándar.

ejemplos/concurrencia/lexer-canal/main.go
// Un lexer concurrente: produce tokens en una goroutine y los envía por un canal.
// El consumidor (el parser) los recibe con range hasta que el canal se cierra.
package main

import (
	"fmt"
	"unicode"
)

type Token struct{ Type, Literal string }

func lex(input string) <-chan Token {
	out := make(chan Token, 4) // buffer: el lexer puede adelantarse hasta 4 tokens
	go func() {
		defer close(out) // cerrar avisa al consumidor que no hay más tokens
		for i := 0; i < len(input); {
			ch := rune(input[i])
			switch {
			case unicode.IsSpace(ch):
				i++
			case unicode.IsLetter(ch):
				start := i
				for i < len(input) && unicode.IsLetter(rune(input[i])) {
					i++
				}
				out <- Token{"IDENT", input[start:i]}
			case unicode.IsDigit(ch):
				start := i
				for i < len(input) && unicode.IsDigit(rune(input[i])) {
					i++
				}
				out <- Token{"INT", input[start:i]}
			default:
				out <- Token{"SYMBOL", string(ch)}
				i++
			}
		}
		out <- Token{"EOF", ""}
	}()
	return out
}

func main() {
	for tok := range lex("let total = precio * 3;") {
		fmt.Printf("%-6s %q\n", tok.Type, tok.Literal)
	}
}
$ go run ./concurrencia/lexer-canal
IDENT  "let"
IDENT  "total"
SYMBOL "="
IDENT  "precio"
SYMBOL "*"
INT    "3"
SYMBOL ";"
EOF    ""
¿Y si el parser deja de leer a la mitad (por ejemplo, por un error de sintaxis)? El lexer quedaría bloqueado para siempre en out <- tok: una goroutine leak. Solución: pasar un context o un canal done y usar select al enviar.

8. select, timeouts y context

select: esperar varios canales a la vez
select {
case tok := <-tokens:
    fmt.Println("token:", tok)
case err := <-errs:
    fmt.Println("error:", err)
case <-time.After(2 * time.Second):
    fmt.Println("timeout: ¿recursión infinita?")
case <-ctx.Done():

default:
    // opcional: no bloquear si nada está listo
}
Evaluar con límite de tiempo
func EvalWithTimeout(program *ast.Program, d time.Duration) (object.Object, error) {
    ctx, cancel := context.WithTimeout(context.Background(), d)
    defer cancel()

    done := make(chan object.Object, 1) // buffer 1: evita leak
    go func() {
        done <- evaluator.Eval(program, object.NewEnvironment())
    }()

    select {
    case res := <-done:
        return res, nil
    case <-ctx.Done():
        return nil, fmt.Errorf("evaluación cancelada: %w", ctx.Err())
    }
}
Ojo: en el ejemplo de la derecha, si se acaba el tiempo la goroutine del evaluador sigue corriendo en segundo plano. Para detenerla de verdad, el evaluador tendría que revisar ctx.Done() periódicamente (por ejemplo, en cada llamada a función). Es un buen reto para el taller.

9. Pipeline, fan-out/fan-in y worker pool

ejemplos/concurrencia/pipeline/main.go
// Worker pool + fan-out/fan-in + context: evaluar muchos programas en paralelo con timeout.
package main

import (
	"context"
	"fmt"
	"strconv"
	"strings"
	"sync"
	"time"
)

type Job struct {
	ID  int
	Src string
}

type Result struct {
	ID    int
	Value int
	Err   error
}

// evalSum "evalúa" programas de la forma "1 + 2 + 3" y simula trabajo lento.
func evalSum(ctx context.Context, src string) (int, error) {
	select {
	case <-time.After(time.Duration(len(src)) * 5 * time.Millisecond):
	case <-ctx.Done():
		return 0, ctx.Err() // cancelado o se acabó el tiempo
	}
	total := 0
	for _, part := range strings.Split(src, "+") {
		n, err := strconv.Atoi(strings.TrimSpace(part))
		if err != nil {
			return 0, fmt.Errorf("token inválido %q", strings.TrimSpace(part))
		}
		total += n
	}
	return total, nil
}

func worker(ctx context.Context, jobs <-chan Job, results chan<- Result, wg *sync.WaitGroup) {
	defer wg.Done()
	for j := range jobs {
		v, err := evalSum(ctx, j.Src)
		results <- Result{ID: j.ID, Value: v, Err: err}
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 150*time.Millisecond)
	defer cancel()

	programs := []string{"1 + 2", "10 + 20 + 30", "4 + x", "1 + 1 + 1 + 1 + 1 + 1 + 1 + 1 + 1"}
	jobs := make(chan Job)
	results := make(chan Result)

	var wg sync.WaitGroup
	for range 2 { // fan-out: 2 workers comparten el canal jobs
		wg.Add(1)
		go worker(ctx, jobs, results, &wg)
	}

	go func() { // productor
		defer close(jobs)
		for i, p := range programs {
			jobs <- Job{ID: i, Src: p}
		}
	}()

	go func() { // fan-in: cerrar results cuando todos los workers terminen
		wg.Wait()
		close(results)
	}()

	for r := range results {
		if r.Err != nil {
			fmt.Printf("programa %d: error: %v\n", r.ID, r.Err)
			continue
		}
		fmt.Printf("programa %d = %d\n", r.ID, r.Value)
	}
}
$ go run ./concurrencia/pipeline (el orden puede variar)
programa 0 = 3
programa 2: error: token inválido "x"
programa 1 = 60
programa 3: error: context deadline exceeded

→
2 workersfan-out
→

  • Fan-out: varios workers leen del mismo canal jobs.
  • Fan-in: todos escriben en results; una goroutine lo cierra tras wg.Wait().
  • context: el programa 3 tarda más que el timeout y se cancela.

10. Errores comunes (y cómo reconocerlos)

ErrorSíntomaSolución
Deadlockfatal error: all goroutines are asleep - deadlock!Que alguien reciba lo que se envía; usar buffer o una goroutine aparte.
Goroutine leakLa memoria crece; goroutines bloqueadas para siempreCancelación con context/done y select.
Enviar a un canal cerradopanic: send on closed channelSolo el emisor cierra, y una sola vez.
Olvidar wg.Wait()El programa termina antes de que las goroutines imprimanAdd antes de go, defer Done() adentro.

11. ¿Dónde encaja la concurrencia en ZeldaInterpreter?

Buenas oportunidades

  • Lexer como goroutine que emite tokens por un canal.
  • Ejecutar un archivo de pruebas .mk por worker en paralelo.
  • REPL con timeout para cortar recursiones infinitas.
  • Un built-in futuro spawn(fn) para lanzar goroutines desde Monkey.

Cuidado

  • El Environment usa un map: los maps de Go no son seguros con escritores concurrentes.
  • Si dos goroutines comparten un entorno, se necesita un sync.RWMutex en Get/Set.
  • El evaluador del libro es secuencial a propósito: más simple de entender y de probar.

12. Ideas clave

Goroutines baratas

go f() y esperar con WaitGroup.

Carreras

x++ no es atómico: Mutex, atomic y -race.

Canales

Sin buffer = encuentro; con buffer = cola acotada. Solo el emisor cierra.

select

Esperar varios eventos: datos, errores, timeouts y cancelación.

context

Propagar cancelación y plazos a través de goroutines.

Patrones

Pipeline, fan-out/fan-in y worker pool resuelven la mayoría de casos.
