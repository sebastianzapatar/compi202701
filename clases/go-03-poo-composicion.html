POO en Go: Objetos, Agregación, Composición y “Herencia”

Go no tiene clases ni herencia, pero sí tiene objetos, encapsulación y polimorfismo. Hoy aprendemos a modelar con structs, métodos, embedding e interfaces, exactamente como lo hace el código de ZeldaInterpreter.

Código ejecutable en ejemplos/poo/ 2 simuladores interactivos
1Traducir los conceptos de POO clásica a sus equivalentes en Go.
2Distinguir asociación, agregación y composición por el ciclo de vida.
3Reutilizar código con embedding y entender por qué no es herencia.
4Diseñar con interfaces pequeñas y polimorfismo implícito.

1. ¿Go es un lenguaje orientado a objetos?

La respuesta oficial de las FAQ de Go es “sí y no”: hay tipos con métodos y un estilo orientado a objetos, pero no hay jerarquía de tipos. Cada idea de la POO clásica tiene un equivalente más simple:

2. Objetos: struct, métodos, constructor y encapsulación

ejemplos/poo/objetos/main.go
// Objetos en Go: struct + métodos + constructor + encapsulación.
package main

import (
	"errors"
	"fmt"
)

// Token es un "objeto valor": datos inmutables con comportamiento.
type Token struct {
	Type    string
	Literal string
}

// String implementa fmt.Stringer: Println lo usa automáticamente.
func (t Token) String() string { return fmt.Sprintf("%s(%q)", t.Type, t.Literal) }

// Cursor encapsula su estado: los campos en minúscula no se ven fuera del paquete.
type Cursor struct {
	input string
	pos   int
}

// NewCursor es el "constructor": valida y entrega el objeto listo para usar.
func NewCursor(input string) (*Cursor, error) {
	if input == "" {
		return nil, errors.New("input vacío")
	}
	return &Cursor{input: input}, nil
}

// Next avanza el cursor (pointer receiver: modifica el estado).
func (c *Cursor) Next() (byte, bool) {
	if c.pos >= len(c.input) {
		return 0, false
	}
	ch := c.input[c.pos]
	c.pos++
	return ch, true
}

// Pos es un "getter": lectura controlada del estado interno.
func (c *Cursor) Pos() int { return c.pos }

func main() {
	t := Token{Type: "INT", Literal: "5"}
	fmt.Println(t) // usa t.String()

	c, err := NewCursor("let")
	if err != nil {
		panic(err)
	}
	for ch, ok := c.Next(); ok; ch, ok = c.Next() {
		fmt.Printf("%c@%d ", ch, c.Pos()-1)
	}
	fmt.Println()

	if _, err := NewCursor(""); err != nil {
		fmt.Println("error:", err)
	}
}
$ go run ./poo/objetos
INT("5")
l@0 e@1 t@2 
error: input vacío

Lo que hay que notar

  • Encapsulación por paquete: fuera de este paquete nadie puede tocar pos; solo Next() y Pos().
  • Constructor que valida: devuelve (*Cursor, error), nunca un objeto a medias.
  • String() convierte a Token en un fmt.Stringer: así funcionan los String() del AST.
  • Valor cero útil: un buen tipo Go funciona aun sin constructor cuando es posible (var b strings.Builder).

3. Receivers y method sets

Que un tipo implemente una interfaz depende de su method set, y este depende del tipo de receiver:

TipoMétodos con receiver TMétodos con receiver *T
Valor TSíNo (en el method set)
Puntero *TSíSí
Por eso el evaluador usa punteros
type Integer struct{ Value int64 }

func (i *Integer) Type() ObjectType { return INTEGER_OBJ }
func (i *Integer) Inspect() string  { return fmt.Sprintf("%d", i.Value) }

var a Object = &Integer{Value: 5} // ✔ *Integer tiene ambos métodos
var b Object = Integer{Value: 5}  // ✘ no compila: Integer no implementa Object

Regla práctica

  • Si el método modifica el estado → receiver puntero.
  • Si el struct es grande → puntero (evita copias).
  • Si un método usa puntero, usa puntero en todos por consistencia.
  • Valores pequeños e inmutables (como Token) → receiver valor.

4. Asociación, agregación y composición

Las tres describen “un objeto tiene/usa otro”. La diferencia está en quién crea la parte y si sobrevive al todo.

Asociación

Relación de uso, a menudo temporal. Un objeto recibe a otro como parámetro.

func (p *Parser) Report(w io.Writer)

UML: línea simple —

Agregación ◇

El todo guarda una referencia a una parte que se creó fuera y puede compartirse. La parte sobrevive al todo.

type REPL struct { out io.Writer }

UML: rombo vacío ◇

Composición ◆

El todo crea y es dueño de la parte. No se comparte y deja de existir con el todo.

type REPL struct { env *Environment }

UML: rombo lleno ◆

ejemplos/poo/agregacion/main.go
// Agregación vs composición.
//   - Agregación: el todo USA una parte que vive fuera de él (se la entregan).
//     Ej.: el REPL y su io.Writer, que puede compartirse con otros.
//   - Composición: el todo CREA y es dueño de sus partes; mueren con él.
//     Ej.: el REPL y su Environment.
package main

import (
	"fmt"
	"io"
	"os"
	"strings"
)

type Environment struct{ store map[string]int }

func NewEnvironment() *Environment { return &Environment{store: map[string]int{}} }

type REPL struct {
	out io.Writer    // agregación: compartido, no le pertenece
	env *Environment // composición: lo crea y es su dueño
}

func NewREPL(out io.Writer) *REPL {
	return &REPL{out: out, env: NewEnvironment()}
}

func (r *REPL) Let(name string, v int) {
	r.env.store[name] = v
	fmt.Fprintf(r.out, "%s = %d\n", name, v)
}

func main() {
	var log strings.Builder
	shared := io.MultiWriter(os.Stdout, &log)

	a := NewREPL(shared)
	b := NewREPL(shared) // ambos REPL agregan el MISMO writer
	a.Let("x", 1)
	b.Let("x", 2)

	// Cada REPL compuso su propio entorno: no se mezclan.
	fmt.Println("x en a:", a.env.store["x"], "| x en b:", b.env.store["x"])

	a, b = nil, nil // los REPL y sus entornos quedan sin referencias (basura)...
	fmt.Print("...pero el writer agregado sigue vivo:\n", log.String())
}
$ go run ./poo/agregacion
x = 1
x = 2
x en a: 1 | x en b: 2
...pero el writer agregado sigue vivo:
x = 1
x = 2
En Go la diferencia es semántica, no sintáctica: ambos casos son un campo puntero. Lo que cambia es quién lo crea (el constructor o el llamador) y quién más lo referencia. Documéntalo en el comentario del campo.

6. “Herencia” en Go: embedding

Al embeber un tipo (campo sin nombre), sus campos y métodos se promueven al tipo externo. Parece herencia, pero es composición: el tipo externo contiene un valor del embebido.

ejemplos/poo/embedding/main.go
// "Herencia" en Go: NO existe. Se usa EMBEDDING (composición con promoción
// de métodos) para reutilizar código, e interfaces para el polimorfismo.
package main

import "fmt"

// BaseNode tiene comportamiento reutilizable.
type BaseNode struct {
	Literal string
}

func (b BaseNode) TokenLiteral() string { return b.Literal }
func (b BaseNode) Kind() string         { return "genérico" }
func (b BaseNode) Describe() string     { return "nodo " + b.Kind() } // llama a SU Kind

// Integer embebe BaseNode: sus métodos se PROMUEVEN a Integer.
type Integer struct {
	BaseNode
	Value int64
}

// Kind oculta (shadowing) al método promovido. No es un override virtual.
func (i Integer) Kind() string { return "entero" }

type Node interface {
	TokenLiteral() string
	Kind() string
}

func main() {
	n := Integer{BaseNode: BaseNode{Literal: "5"}, Value: 5}

	fmt.Println(n.TokenLiteral())  // promovido desde BaseNode
	fmt.Println(n.Kind())          // método propio de Integer
	fmt.Println(n.BaseNode.Kind()) // acceso explícito al embebido
	fmt.Println(n.Describe())      // ¡"nodo genérico"! No hay despacho virtual

	var node Node = n // Integer satisface Node gracias a los métodos promovidos
	fmt.Println(node.Kind())
}
$ go run ./poo/embedding
5
entero
genérico
nodo genérico
entero
La trampa clásica: n.Describe() imprime “nodo genérico”, no “nodo entero”. Dentro de BaseNode.Describe, el receiver es un BaseNode y no sabe nada de Integer. En Go no hay métodos virtuales: si necesitas que el comportamiento varíe, usa una interfaz.
Herencia (Java)Embedding (Go)
Relación “es un”Relación “tiene un” con atajos
super.metodo()n.BaseNode.Metodo()
Override con despacho virtualShadowing, sin despacho virtual
Subtipo asignable a la clase baseInteger no es asignable a BaseNode

8. Embedding de interfaces (y de punteros)

Interfaces que se componen
// Biblioteca estándar
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
type ReadWriter interface {
    Reader
    Writer
}

// ast/ast.go — ¡ya lo usamos en la Semana 4!
type Statement interface {
    Node            // embebe la interfaz Node
    statementNode()
}
Embeber un puntero y conflictos
type Logger struct{ prefix string }
func (l *Logger) Log(msg string) { fmt.Println(l.prefix + msg) }

type Parser struct {
    *Logger            // embebe un puntero: se comparte
    errors []string
}

p := Parser{Logger: &Logger{prefix: "[parser] "}}
p.Log("inicio")        // promovido desde *Logger

// Si dos embebidos al MISMO nivel tienen Log(),
// p.Log() es un error de compilación: "ambiguous selector".
Interfaces pequeñas: en Go las mejores interfaces tienen uno o dos métodos (io.Reader, fmt.Stringer, error) y se combinan por embedding cuando hace falta.

9. Polimorfismo con interfaces implícitas

ejemplos/poo/polimorfismo/main.go
// Polimorfismo con interfaces: muchos tipos, un mismo contrato.
package main

import (
	"fmt"
	"strings"
)

type Object interface {
	Type() string
	Inspect() string
}

type Integer struct{ Value int64 }
type Boolean struct{ Value bool }
type Array struct{ Elements []Object }

func (i *Integer) Type() string    { return "INTEGER" }
func (i *Integer) Inspect() string { return fmt.Sprint(i.Value) }
func (b *Boolean) Type() string    { return "BOOLEAN" }
func (b *Boolean) Inspect() string { return fmt.Sprint(b.Value) }
func (a *Array) Type() string      { return "ARRAY" }
func (a *Array) Inspect() string {
	parts := make([]string, len(a.Elements))
	for i, e := range a.Elements {
		parts[i] = e.Inspect() // cada elemento sabe imprimirse a sí mismo
	}
	return "[" + strings.Join(parts, ", ") + "]"
}

// Verificación en tiempo de compilación: si un tipo deja de cumplir Object, no compila.
var (
	_ Object = (*Integer)(nil)
	_ Object = (*Boolean)(nil)
	_ Object = (*Array)(nil)
)

func truthy(o Object) bool {
	switch v := o.(type) { // type switch: decidir según el tipo concreto
	case *Boolean:
		return v.Value
	default:
		return true
	}
}

func main() {
	objs := []Object{
		&Integer{Value: 5},
		&Boolean{Value: false},
		&Array{Elements: []Object{&Integer{Value: 1}, &Boolean{Value: true}}},
	}
	for _, o := range objs {
		fmt.Printf("%-7s %-12s truthy=%v\n", o.Type(), o.Inspect(), truthy(o))
	}
}
$ go run ./poo/polimorfismo
INTEGER 5            truthy=true
BOOLEAN false        truthy=false
ARRAY   [1, true]    truthy=true

Dos formas de polimorfismo

  • Despacho dinámico: o.Inspect() llama al método del tipo concreto.
  • Type switch: el código cliente decide según el tipo (así funciona Eval).
  • var _ Object = (*Integer)(nil) obliga al compilador a verificar que el tipo cumple la interfaz.

10. Composición sobre herencia (y SOLID en Go)

S · Responsabilidad única

lexer, parser y evaluator son paquetes separados con un solo motivo de cambio cada uno.

O · Abierto/cerrado

Agregar un operador es registrar una función (registerInfix) sin modificar parseExpression.

L · Sustitución de Liskov

Cualquier object.Object debe poder imprimirse con Inspect() sin sorpresas.

I · Segregación de interfaces

Interfaces pequeñas: Node solo pide TokenLiteral() y String().

D · Inversión de dependencias

“Acepta interfaces, devuelve structs”: repl.Start(in io.Reader, out io.Writer).

Composición

Combinar piezas pequeñas es más flexible que una jerarquía profunda de clases.
